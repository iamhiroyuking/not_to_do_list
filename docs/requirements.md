# Not To Do — 要件定義 v2

v1（`要件定義書_v1.docx`）を引き継ぎ、2026-08-23の設計判断を反映したもの。
**根本は変えていない。変えたのは重心と、報酬の払い方。**

---

## 1. このアプリは何か

既存のTo Doリストが「やるべきこと」をまとめるものであるのに対し、
限られた時間を使うために本当に必要なのは「**何をやらないべきか**」を精査すること。

人間は無意識のうちに楽な方向へ流される。**その兆候を未然に可視化して防ぐ**のが
このアプリである。（v1 1.2 より。ここは変えない）

### 1.1 重心 — 2026-08-23に確定

**第一の目的は「自分の失敗パターンを記録すること」。**
悪い習慣をやめられるのは、その**結果**であって目的ではない。

この一行が、以下すべての判断の根拠になる。

| | v1の暗黙の重心 | v2で確定した重心 |
|---|---|---|
| 主役 | 我慢の連続日数を伸ばす | 失敗のパターンを観測する |
| 一番の資産 | ストリークの数字 | **失敗の理由（`DailyRecord.note`）** |
| 最も避けたいこと | 我慢が途切れること | **記録が途切れること** |

**最も重い罪は「破ること」ではなく「記録しないこと」。**
破った日は、理由さえ書けば観測が成立している。何も書かなかった日だけが、
このアプリにとって完全な損失になる。

ただしこれを**罰則で表現しない**（→ 7章）。記録しなかった日にペナルティを課すと、
入力のハードルが上がり、かえって記録が減る。この重さは「観測日数が折れる」という
事実として静かに示すだけにとどめ、記録を促す仕事は4章の設計が担う。

### 1.2 この重心から出る帰結

- 失敗（FAIL）を記録した人は**祝われる**。入力できたこと自体に価値がある
- 折れない数字（記録した日数）が主役、折れる数字（我慢の連続）は従
- 記録し忘れた日は、後から埋められる
- 報酬は「我慢できた量」ではなく「観測できた量」に対して払う

## 2. ターゲットと利用シーン

**ターゲット**（v1 2.1 を維持）— 学生や社会人など、時間に追われている人。

**利用シーンは2つだけ。この2つ以外は設計しない。**

| | いつ | 何をする | どこから |
|---|---|---|---|
| **A. 夜の振り返り** | 1日1回、夜 | その日の各項目にKEEP / FAILを付ける。FAILなら理由を書く | 通知 → ウィジェット → アプリ |
| **B. 思いついた時の追加** | 不定期 | 「明日はこれをやりたくない」を登録する | ウィジェット → アプリ |

Aは**1日1回**であり、誘惑を感じた瞬間に開くアプリではない。
記録の単位は「日」で確定する。

## 3. 中核の仕組み

### 3.1 1日の状態は4つ

| 状態 | 意味 | 観測 |
|---|---|---|
| **KEEP** | 我慢できた | ✅ できている |
| **FAIL＋理由あり** | 破った。ただし理由を書けた | ✅ できている |
| **FAIL＋理由なし** | 破った。理由が残っていない | ⚠️ 不完全 |
| **未記録** | 何も入力しなかった | ❌ できていない |

### 3.2 数字は2つ。役割を厳密に分ける

v1の実装では、この2つが**同じ炎マークと「連続」という同じ言葉**で表示され、
利用者から見て区別できなくなっていた。v2では語彙も記号も分ける。

#### ① 観測日数 ＝ **主役。折れにくい**

記録をつけた日数。KEEPでもFAILでも増える。

- 累計と連続の両方を持つ
- **未記録の日だけが連続を切る**
- 炎（🔥）は使わない。積み上がる別の記号を割り当てる
- FAILを記録した時に祝うのは**この数字**

#### ② 連続KEEP ＝ **従。項目ごとの成績**

我慢が続いている日数。項目ごとに持つ。炎（🔥）はこちらに割り当てる。

**判定ルール（2026-08-23確定）:**

| 今日の状態 | 連続KEEPはどうなるか |
|---|---|
| KEEP | +1 |
| KEEP以外／前日はKEEP | **据え置き（セーフ）** |
| KEEP以外／前日もKEEP以外 | **0にリセット（アウト）** |

> **「1日は転んでいい。2日続けて転んだら立て直す。」**

FAIL・理由なしFAIL・未記録を**すべて同じ「KEEP以外」として扱う**。
理由の有無でも、記録の有無でも差を付けない。ルールはこの1本だけ。

この単純さは意図的なものである。判定を複雑にすると、
利用者が「今日どう入力すれば連続が守れるか」を計算し始める。
それは観測の歪み（自分に都合よく記録する）を生み、1.1の重心を損なう。

**この判定ルールは、アプリ内のコラム `action5`「完璧じゃなくても戻る」で
すでに説明しているもの（Never miss twice）と一致する。**
アプリの仕組みと、アプリが教えている内容が同じことを言っている状態にする。

### 3.3 遡及入力

記録し忘れた日は、**カレンダーから後で埋められる。ただし前日ぶんのみ**（2026-08-23確定）。

遡れる範囲（1日）と、連続KEEPの猶予（1日）を**意図的に一致させている**。
「昨日つけ忘れた」は今日埋めれば間に合う。それより前は埋められない。

- 期限内に埋めた場合、観測日数の連続も**復活する**（猶予の中なので「間に合った」扱い）
- ただし後から埋めた記録には `isBackfilled` の印を残し、分析画面では区別できるようにする。
  **数字の上では救済するが、データとしての正直さは失わない**
- 範囲を1日に絞るのは、まとめて過去を埋める行為を防ぐため。
  1週間ぶんを思い出しながら書いた記録は、観測ではなく創作になる

## 4. 継続的に入力してもらうための設計

「記録が第一」である以上、**入力してもらえなければアプリとして成立しない**。
入力が続く条件を3層に分けて設計する。

### 層1｜入力コストを下げる

v1では、記録に到達するまでに
`起動 → スプラッシュ1.5秒 → マインドセット画面 → ボタン → リスト → タップ` を要した。
**「アプリを開く」という判断自体が最大の関門**であり、これを回避する経路が無かった。

- **記録ウィジェット** — ホーム画面／ロック画面から直接KEEP / FAILを付ける（App Intents）
- **追加ウィジェット** — タップで追加画面へ（利用シーンB用）
- **通知から直接記録** — 通知を長押しして、その場でKEEP / FAILを押せる（`UNNotificationAction`）
- **起動時のマインドセット画面を廃止** — 層2へ移す

### 層2｜入力に報酬を返す

**報酬が入力の邪魔をしないこと（2026-08-24に修正）。**
当初は記録するたびにお祝いのモーダルを出していたが、項目が4つあれば
4回モーダルを閉じさせることになり、層1（入力コストを下げる）と正面から衝突していた。

- モーダルのお祝いは**1日1回だけ**
- 主役の数字（観測日数）はリスト最上部に**常に出す**ので、報酬は消えていない

**報酬は「見えていること」で足りる。毎回止めて祝う必要はない。**


**v1は報酬（コラム）を入力の"前"に置いていた。v2では"後"に置く。**

```
v1:  起動 → マインドセット（報酬）→ リスト（コスト）
v2:  起動 → リスト（コスト）→ 記録 → マインドセット（報酬）
```

同じ部品の順番を入れ替えるだけで、意味が反転する。入力が報酬の引き金になり、
毎回の起動摩擦（層1）も同時に消える。

祝う対象は**観測日数**（3.2①）。FAILでも祝う。ただし文言で何を祝ったかを明示する。

- ❌ v1: FAILの直後に「🔥 連続記録更新！」（我慢が折れたのに炎が出る）
- ✅ v2: 「記録した。それがいちばん難しい。」＋ 観測日数

### 層3｜空白を見せる

v1のカレンダーは「記録がある日＝青丸」のみで、
**FAILした日と、何も入力しなかった日が同じ見た目**だった。

KEEP / FAIL / 未記録を色で分ける。埋まっていないマスが見えることが、
戻ってくる理由と遡及入力（3.3）の入口になる。

### 層3.5｜記録する瞬間に予測を見せる（2026-08-24に追加）

危険シグナルはリストの小さなグレー文字に切り詰められていて、
**いちばん効くはずの瞬間＝破ってしまった直後に出てこなかった。**

失敗の記録をアラートから画面（`RecordFailView`）へ作り替え、
そこに「あなたが予測していた危険シグナル」を出す。

- 当てはまるならタップ1回で理由が埋まる → **入力が減る**
- 同時に「予測は当たっていたか」（`DailyRecord.matchedPrediction`）が記録される
  → 分析画面（5.1）に的中率として出る

**入力を増やさずに、分析の材料が増える形にしたのが要点。**
分析画面を開かなくても、記録するたびに 予測→観測 のループがその場で閉じる。

### 層4｜未然に防ぐ ＝ 危険シグナルを働かせる

v1では `warningSignal`（危険シグナル）が**入力されたきり誰も読み返さないデータ**だった。
1.2の「兆候を未然に可視化して防ぐ」が、実装上どこでも動いていなかった。

**通知に危険シグナルを載せる。**

> 「負けを取り返そうと焦っている時」— 今、そうなっていませんか？

これは記録させるための仕掛けではなく、**記録より前に効く**仕掛けである。

## 5. 画面

| 画面 | 役割 | v1からの変更 | 実装 |
|---|---|---|---|
| リスト | 今日の記録をつける | 数字の表示を3.2に沿って修正、メインを上に固定 | ✅ |
| カレンダー | 振り返りと遡及入力 | 3状態の色分け、タップで遡及入力 | ✅ |
| **分析** | **失敗パターンを見る** | **新規。v1 6章にあったが未実装だった** | ✅ |
| コラム | 読み物 | 継続 | ✅ |
| 設定 | 通知・外観・データ | 外観を3択に | ✅ |
| マインドセット | 記録直後の報酬 | 起動時 → 記録直後へ移動 | ✅ |

### 5.1 分析画面 — v2の主役

重心が「失敗パターンの記録」である以上、**集めた記録を見せる画面がアプリの核心**になる。
v1では失敗理由が詳細画面の奥に埋もれ、集計する場所が無かった。

出すもの：

1. **予測 vs 実際** — 登録した危険シグナル（事前の予測）と、実際に書かれた失敗理由（事後の観測）の突き合わせ。**予測は当たっていたか。** これがこのアプリ独自の分析
2. **失敗の分布** — 曜日別・項目別。「いつ崩れるか」
3. **理由の一覧** — 時系列で読み返せる形

### 5.2 項目の数

**メイン3個＋サブで合計5〜10個**を想定（利用者による）。

- メインに指定した項目**だけ**がウィジェットと通知に出る
- リストではメインを上に固定して表示する
- サブはリストを下へたどれば記録できる

## 6. データモデル

```
NotToDoItem
  title           習慣の名前
  warningSignal   危険シグナル（失敗しやすい状況の事前予測）
  isFocused       メイン3個かどうか  ← 新規（5.2）
  createdAt
  records         → DailyRecord (1対多, cascade削除)

DailyRecord
  date
  isSuccess       KEEP / FAIL
  note            失敗の理由 ← このアプリで最も価値のあるデータ
  isBackfilled       後から埋めたか  ← 新規（3.3）
  matchedPrediction  危険シグナルの予測どおりだったか ← 新規（5.1）
  item               → NotToDoItem
```

**v1から削除するもの**

- `NotToDoItem.isActive` — 一度も使われていない
- `@AppStorage("currentLoginStreak")` — 観測日数として記録から計算し直す。
  `@AppStorage` に持つと、記録を消しても数字が残り、実データと食い違う

## 7. 決着した論点

### FAILを祝うのは正しい（2026-08-23）

「失敗を記録したのに祝われるのはおかしい」という指摘を検討したが、**却下した**。
1.1の重心により、**入力できたこと自体に価値がある**。
v1の実装は意図としては正しく、問題は「我慢の連続」と同じ炎・同じ言葉を
使っていたために、**何を祝われたのか利用者に伝わらなかった**ことにある。
祝う行為ではなく、語彙と記号を分けることで解決する（3.2）。

### 節約時間・回避した損失を要件から落とす（2026-08-23）

v1 2.2 で競合優位性として挙げ、3.3 でも機能要件としていたが、**v2で落とす**。

「SNSを見ない＝1回30分」を積み上げる仕組みは、**KEEPした時にしか報われない**。
報酬の軸がFAIL側を完全に無視するため、1.1の重心とぶつかる。
報酬は「我慢できた量」ではなく「観測できた量」に対して払う（層2）。

代わりに報酬の軸となるのは、観測日数（3.2①）と分析画面（5.1）である。

### 判定ルールを1本にまとめた（2026-08-23）

検討の途中では「未記録の日を最も重く扱う」（破った日は据え置き、
何も書かなかった日は即リセット）という案を採っていた。
「破ってもいいから書け」をルール自体で表現する狙いだった。

**この案は却下した。** 理由が空欄のFAILも、未記録も、すべて同じ「KEEP以外」として
1日の猶予を与える。

罰則で記録を促すのをやめ、**摩擦を下げることで記録を促す**方針に切り替えたため。
記録を促す仕掛けは、判定ルールではなく4章（ウィジェット・通知・報酬・空白の可視化）が担う。
入力のハードルを上げる方向の判断は、すべて重心（1.1）に反する。

その代わり、**観測日数（3.2①）だけは正直に折れる**。
連続KEEPは寛容に、観測日数は厳密に。2つの数字の役割分担がここで完成する。

## 8. 決着した細目（2026-08-23）

| 論点 | 決定 | 理由 |
|---|---|---|
| 理由が空欄のFAIL | **セーフ扱い** | 入力した事実を優先する。空欄を罰すると入力自体をやめる |
| 未記録の日 | **1日の猶予を置く** | 上と揃える。2日続いたらリセット |
| 遡及入力の範囲 | **前日ぶんのみ** | 猶予期間と一致させる。まとめ書きは観測でなく創作になる |
| コラムの記述 | **断定を下げる＋出典を付ける** | → `docs/column-revision.md` とGitHub Issue |

### 残っている未決

- **観測日数の記号を何にするか。** 炎（🔥）は連続KEEPに使うため、別の記号が要る。
  積み上がることが伝わるもの（マス目・積み木・書き込まれたページなど）
- **メイン3個の選び方。** 利用者が明示的に指定するか、上位3件を自動でメインにするか

## 10. テスト

XCTestのターゲットは置いていない。判定ロジック（3.2）だけを、依存なしで走る
スクリプトとして検証できるようにしてある。

```
swift Tests/StreakLogicTests.swift
```

`Tests/` はソースフォルダ（`not_to_do_list/`）の外にあるため、
フォルダ同期方式でもアプリのバンドルには入らない。

**UIのテストは書かない。** 対象は連続KEEPと観測日数の計算に限る。

### 取り違えやすい点

「据え置き」は**加算しない**。`KEEP → FAIL → KEEP` は 3 ではなく **2** になる。
FAILの日は折れないだけで、KEEPの日数としては数えないため。
テストの名前にこれを明記してある。
